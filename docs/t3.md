# T3 Code as an optional Environment service

Runner can host an **unmodified T3 Code server** alongside its native Codex/Grok
Agent and direct commands. T3 owns projects, threads, agent interactions,
worktrees, approvals, terminal, web UI, pairing and orchestration MCP. Runner
owns only Environment lifecycle, installation, provider setup and transport.
This capability is not tied to a particular target repository or test suite.

## Start and use

```json
{"executor":"codex","services":["t3"],"idempotencyKey":"<fresh stable key>"}
```

Pass the object above to `open_environment`. With no `services` property,
Runner behaves as before. This is the branch's API contract; verify that the
deployed API accepts `services` before attempting deployed acceptance. A local
checkout or a refreshed client does not update the deployed control plane.
On creation Runner installs the official T3 CLI,
starts `t3 serve` on local loopback, starts a Cloudflare Quick Tunnel and
reports the **origin only** in the owner-authorized `inspect_environment`
snapshot under `services.t3`. T3's state is `starting`, `ready`,
`failed`, `stopped`, or `unavailable` (control-plane observation is not current).
A ready Environment does not imply a healthy T3
service after a subsequent T3 process failure. Use the observed service status.

Runner never returns the T3 native pairing token in ordinary MCP output,
resources, logs, metadata or artifacts. Owners use T3's **native pairing**
procedure to authorize their own browser or external client. Use the Workbench's
**Verify identity and connect T3** action described below. For manual native
pairing from a trusted private host terminal,
`t3 auth pairing create --base-url <reported-https-origin> --ttl 5m --json`
issues a fresh credential. **Do not ask an untrusted agent to print or copy
pairing output through command/Agent logs.** Use a trusted private terminal
or owner-controlled channel for sensitive pairing. T3's own T3 Connect flow
may be used if separately configured. Public HTTPS alone is not a grant.

When connected, use T3 web/mobile clients or T3's documented external OAuth
MCP at `<origin>/mcp`. Only the selected user/agent permissions are granted.
T3's documented external MCP has project, thread, run and provider tools; it
does not promise token-level push streaming for unrelated clients.

## Provider configuration

Runner first applies its existing `configureProvider()` setup to the selected
native executor's `HOME`. T3 sees that native provider configuration and an
explicit allowlist of environment variables, including the existing provider
key and fixed Agent GitHub work token. For Grok it also supplies the same
key as `XAI_API_KEY`, matching Runner’s native Grok process and upstream T3’s
authentication probe. The official Grok install directory is included in PATH. It does **not** receive GitHub Actions
OIDC or workflow-dispatch credentials. No second model secret or custom base
URL is copied into T3's own database.

An installed provider can only execute if its actual T3 integration recognizes
that provider and its credentials. Auth checks of Runner's native ACP Agent
are **not** a substitute for a T3-launched Agent run. Other providers can be
enabled using T3's own supported settings and login, as on any standalone
server.

## Environment lifecycle and trust

The T3 process and tunnel are managed by the owning Environment runtime,
not by a direct `command` call. They survive command/Agent turns. When T3
is enabled, the Environment is held until explicit close or its existing
hard deadline; the ordinary 15-minute idle deadline does not automatically
stop an active, owner-requested interactive T3 service. This consumes an
Environment slot and GitHub Actions runtime budget.

T3 listens only on `127.0.0.1`; cloudflared is the public HTTPS transport.
The cloudflared process receives **only** PATH/HOME/TMPDIR, never the model key,
Provider endpoint or GitHub work credentials. Runner checks the live public HTTPS
`/.well-known/t3/environment` descriptor (server version, identity and
capabilities) and matches its identity and version to the local native server before reporting `services.t3.status=ready`. If the tunnel
cannot reach T3 within the bounded startup window, opening fails closed.
The tunnel is temporary and not a stable hostname. Pairing/permissions are
enforced by T3, not by Cloudflare URL secrecy. Runner is **not** a process-level
sandbox: T3 terminals and agent processes share the temporary runner user and
can reach user-readable files and the expressly provided work credentials.
Only grant this service to trusted Principals and use the minimum necessary
T3 scopes. Closing the Environment terminates the T3 and tunnel processes.
Startup is also bounded by the claimed hard deadline. Cleanup kills descendants
in each managed process group even if its leader has already exited, and reports
failure if process cleanup cannot be confirmed. Processes that deliberately leave
the group still require final Environment/job teardown. Changes made to remote
Git repositories cannot be rolled back by closing.

The official T3 server and local `t3` CLI share the normal T3 data directory
under `HOME` for native interoperability; it is ephemeral with the runner.
Save desired files by pushing or exporting them before closing.

## Verification

Deterministic tests (without model keys):
- `node --test tests/t3-provider.test.ts tests/t3-connection.test.ts tests/t3-service.test.ts`
- `npx tsc --noEmit -p .github/actions/agent-runtime` after dependencies are installed
- `node --test tests/*.test.ts` and workflow lint

Live checks use an already installed official T3 CLI (default pinned release
**0.1.5**). Install the Agent runtime dependencies first. The reusable runner
creates a fresh private HOME and Git project, uses the real managed service,
captures all native stdout/stderr privately, revokes its probe credentials,
closes the service and checks process/listener cleanup. SIGINT/SIGTERM also
stop its detached test processes, T3 and tunnel. It removes its temporary
HOME on completion. Do not run it concurrently on port 3773.

```sh
npm ci --prefix .github/actions/agent-runtime
T3_ACCEPTANCE=1 T3_LIVE_BINARY="$HOME/.local/bin/t3" node tests/run-t3-acceptance.ts
```

This proves local HTTP identity, native CLI state and OAuth MCP without provider
keys. The model test is explicitly skipped. To exercise **public HTTPS**, install
`cloudflared`, put it on PATH and add `T3_ACCEPTANCE_REMOTE=1`; the runner then
uses a real Quick Tunnel and sends the independent MCP SDK through its public
origin. It verifies local/public identity and OAuth metadata/issuer before
releasing a pairing code, and rejects HTTP redirects on credentialed MCP requests.

For a **credentialed provider run**, use a trusted disposable environment with
already authorized `MINI_END_USER_KEY` and the selected `MINI_*_BASE_URL` in its
private environment. Install the selected native provider binary first. Add:

```sh
T3_ACCEPTANCE=1 T3_LIVE_BINARY="$HOME/.local/bin/t3" \
T3_LIVE_MODEL=1 T3_LIVE_TRUSTED=1 \
T3_LIVE_PROVIDER=codex T3_LIVE_MODEL_ID=gpt-6.1-sol \
node tests/run-t3-acceptance.ts
```

Repeat with `T3_LIVE_PROVIDER=grok T3_LIVE_MODEL_ID=grok-4.7`. This can incur model
cost. Model runs refuse `pull_request` and `pull_request_target` event contexts;
never expose provider secrets to PR code or add them to the smoke workflow.
The runner configures the selected native provider in its disposable HOME,
enables that built-in provider/custom model through native scoped settings RPC,
and invokes `thread start --provider … --model … --wait --json`. No provider
key is written into T3 settings. It checks a fresh exact nonce reply, matching
provider/model/run IDs, completed authoritative thread state, no active run or
pending requests, and the persisted assistant reply. Nonzero exit and waiting
states fail; native failure text never reaches the reporter. The runner prints
fixed outcomes and validated test counts, never model text or credentials.

For an **existing** T3 server, `T3_LIVE=1 node --test tests/t3-live.test.ts` and
`T3_MCP_LIVE=1 node --test tests/t3-mcp.test.ts` remain available. Set
`T3_LIVE_ORIGIN=https://<origin>`, `T3_MCP_URL=https://<origin>/mcp` and
`T3_LOCAL_ORIGIN=http://127.0.0.1:<port>` as appropriate. `T3_LIVE_BINARY` selects
the CLI, which must share the server's native HOME/data directory. An existing
server model test additionally requires the same explicit trust/provider/model
flags above, `T3_LIVE=1`, and an absolute `T3_LIVE_PROJECT` disposable project.
Enable the provider through T3's normal settings before this test.

Keep the original G0–G5 definitions when reporting acceptance. Complete G0,
then G1; use that deployed Environment for G2–G4 and finish with G5. Disposable
local checks help isolate problems but do not complete deployed gates.

| Gate | Required evidence |
| --- | --- |
| G0 — repository / browser CI | Type checks, repository tests, official T3 smoke and credential-free browser fixtures pass for the exact Runner revision |
| G1 — deployed Environment | Owner-authorized deployed AgentEnv2 API accepts `services:["t3"]`, creates the actual Environment and reports a live, identity-matched service |
| G2 — T3 Provider inference | Actual T3-launched Codex **and** Grok nonce replies with completed native run/thread state in the G1 Environment |
| G3 — owner browser / native Web UI | Real owner completes Runner GitHub login and native pairing remotely, then exercises terminal, Git/worktree, diff and approval in the G1 Environment; a different owner is denied |
| G4 — external OAuth MCP | Independent MCP SDK uses G1's public HTTPS origin, native OAuth/PKCE and real user approval; exercises project reads, thread creation/mutation and run observation with allowed scopes, permission denial and revocation |
| G5 — lifecycle / failure / cleanup | T3 survives ordinary operation completion and the idle interval; native server/tunnel failure is reported and runtime disconnect makes service observations unavailable; explicit close and hard deadline clean up processes; the deployed Environment and exact GitHub Actions job reach confirmed closure |

For G3, check browser binding and single-use login state, reauthentication,
wrong-owner refusal, and refusal after close. Test a pairing request already in
flight when the service fails, its origin changes, the runtime disconnects, or
the Environment closes. Local OAuth fixtures and private-channel tests cover
these protocol boundaries; they do not prove real GitHub or T3 browser UX.

For G5, use separate disposable Environments for explicit close and hard-deadline
expiry. Observe T3 beyond the ordinary 15-minute idle interval with no operation
running, then verify process/listener shutdown, revoked connectivity, Environment
closure and the exact workflow run/attempt's terminal state. A `closing` snapshot
is only close intent. Preserve desired work before destructive lifecycle checks.

A skipped test is not acceptance. Local process/deadline tests do not prove
remote job teardown. Headless pairing-code approval does not prove the browser
OAuth approval UX. If deployed `open_environment` rejects `services` or the
owner-authorized API is unavailable, record that blocker; branch code and a
local T3 process do not prove deployment. Never bypass that boundary with the
fixed Agent GitHub token.

Both install workflows default to `T3CODE_VERSION=0.1.5`; the repository variable
can override it for an explicitly revalidated release. Set
`T3_ACCEPTANCE_VERSION` to the same release when running acceptance manually.
Record release, provider/model, Runner revision and separate gate outcomes in
private acceptance evidence, with no pairing URLs, tokens or raw provider output.

## Owner-only native pairing

When T3 is ready, the owner-private Environment inspection provides a
`services.t3.accessUrl` pointing at the Runner control plane. The Workbench
**Verify identity and connect T3** action opens this URL, **not** a pairing
credential. The browser follows Runner's existing GitHub OAuth authorization-code
flow with PKCE, a single-use state and an HttpOnly browser-binding cookie. The
GitHub numeric user identity is checked against the owning Environment before
a native T3 pairing credential is requested.

The authorized control plane sends a one-time pairing request over the exact
generation-bound runtime WebSocket. The runtime invokes `t3 auth pairing create`
on the host with `--ttl 5m --json` and its observed HTTPS tunnel origin, then
passes the pair URL back only through the still-open private request, not through
standard Task, MCP or Resource outputs or durable state. The browser is
redirected directly to T3's `/pair` page. The pairing token is in the URL
fragment and will never be included in the request URL sent to T3's HTTP server.
All T3 permissions remain native. Re-authenticate to mint a fresh pairing link;
a closed Environment cannot issue one. Results are rechecked against the current
service generation and origin before release. Close intent refuses outstanding
requests immediately, and loss of the private runtime socket aborts its pairing
work without stopping unrelated Environment operations.

## Headless MCP verification

For independent nonproduction deployment prerequisites, offline configuration
preparation and remaining live tests, use the
[isolated staging acceptance procedure](development/t3-staging.md).

The credential-free `T3 service smoke` workflow uses the official MCP SDK
to perform an actual **OAuth authorization-code + PKCE** sequence against native
T3. It registers a client, creates a short-lived native pairing code with the
read-only scope, approves the client, exchanges the code, and uses the resulting
MCP bearer token to verify tool discovery, a real project read, mutation
denial and post-revocation denial. The temporary code and token stay only in
the test process and are not printed. Normal `t3 auth session issue` credentials
are **not MCP client credentials** and must not be used as an MCP shortcut.
This protocol proof does not imply the user-facing Web OAuth approval UX has
been manually accepted.

The disposable harness also obtains a separate operate-scoped OAuth grant and
creates an idle thread without a message or attachments, renames it, reads its
authoritative state, waits for idle and archives it. No provider turn is started;
this covers thread metadata mutations, not send/active-run observation. This
mutation path requires `T3_MCP_DISPOSABLE_MUTATIONS=1`, set automatically only
inside the fresh disposable harness. An idle-only native provider setting is
configured through T3's normal settings API without provider credentials.

The optional model test uses the official `thread start --wait --json` command
and checks the completed provider reply and native terminal state. The native
Runner ACP Agent is a separate execution path.
