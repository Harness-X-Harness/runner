# T3 Code as an optional Environment service

Runner can host an **unmodified T3 Code server** alongside its native Codex/Grok
Agent and direct commands. T3 owns projects, threads, agent interactions,
worktrees, approvals, terminal, web UI, pairing and orchestration MCP. Runner
owns only Environment lifecycle, installation, provider setup and transport.
This capability is not tied to a particular target repository or test suite.

## Start and use

```json
{"executor":"codex","services":["t3"],"idempotencyKey":"<fresh stable key>"}
```

Pass the object above to `open_environment`. With no `services` property,
Runner behaves as before. On creation Runner installs the official T3 CLI,
starts `t3 serve` on local loopback, starts a Cloudflare Quick Tunnel and
reports the **origin only** in the owner-authorized `inspect_environment`
snapshot under `services.t3`. T3's state is either `starting`, `ready`,
`failed`, or `stopped`. A ready Environment does not imply a healthy T3
service after a subsequent T3 process failure. Use the observed service status.

Runner never returns the T3 native pairing token in ordinary MCP output,
resources, logs, metadata or artifacts. Owners use T3's **native pairing**
procedure to authorize their own browser or external client. On the host,
`t3 auth pairing create --base-url <reported-https-origin> --ttl 5h --json`
issues a fresh credential. **Do not ask an untrusted agent to print or copy
pairing output through command/Agent logs.** Use a trusted private terminal
or owner-controlled channel for sensitive pairing. T3's own T3 Connect flow
may be used if separately configured. Public HTTPS alone is not a grant.

When connected, use T3 web/mobile clients or T3's documented external OAuth
MCP at `<origin>/mcp`. Only the selected user/agent permissions are granted.
T3's documented external MCP has project, thread, run and provider tools; it
does not promise token-level push streaming for unrelated clients.

## Provider configuration

Runner first applies its existing `configureProvider()` setup to the selected
native executor's `HOME`. T3 sees that native provider configuration and an
explicit allowlist of environment variables, including the existing provider
key and fixed Agent GitHub work token. It does **not** receive GitHub Actions
OIDC or workflow-dispatch credentials. No second model secret or custom base
URL is copied into T3's own database.

An installed provider can only execute if its actual T3 integration recognizes
that provider and its credentials. Auth checks of Runner's native ACP Agent
are **not** a substitute for a T3-launched Agent run. Other providers can be
enabled using T3's own supported settings and login, as on any standalone
server.

## Environment lifecycle and trust

The T3 process and tunnel are managed by the owning Environment runtime,
not by a direct `command` call. They survive command/Agent turns. When T3
is enabled, the Environment is held until explicit close or its existing
hard deadline; the ordinary 15-minute idle deadline does not automatically
stop an active, owner-requested interactive T3 service. This consumes an
Environment slot and GitHub Actions runtime budget.

T3 listens only on `127.0.0.1`; cloudflared is the public HTTPS transport.
The cloudflared process receives **only** PATH/HOME/TMPDIR, never the model key,
Provider endpoint or GitHub work credentials.
The tunnel is temporary and not a stable hostname. Pairing/permissions are
enforced by T3, not by Cloudflare URL secrecy. Runner is **not** a process-level
sandbox: T3 terminals and agent processes share the temporary runner user and
can reach user-readable files and the expressly provided work credentials.
Only grant this service to trusted Principals and use the minimum necessary
T3 scopes. Closing the Environment terminates the T3 and tunnel processes.
Changes made to remote Git repositories cannot be rolled back by closing.

The official T3 server and local `t3` CLI share the normal T3 data directory
under `HOME` for native interoperability; it is ephemeral with the runner.
Save desired files by pushing or exporting them before closing.

## Verification

Deterministic tests (without model keys):
- `node --test tests/t3-provider.test.ts tests/t3-connection.test.ts tests/t3-service.test.ts`
- `npx tsc --noEmit -p .github/actions/agent-runtime` after dependencies are installed
- `node --test tests/*.test.ts` and workflow lint

Live, **not simulated** checks on a trusted temporary Environment:
- `T3_LIVE=1 node --test tests/t3-live.test.ts` checks the real T3 HTTP and CLI.
- An authorized separate check must actually run a model through T3, not
  through Runner's separate `agent` tool. Set `T3_LIVE_MODEL=1` and
  `T3_LIVE_PROJECT=<disposable project>` only when a real provider is enabled.
- Human access acceptance verifies T3's native pairing, web UI, Git/worktree,
  approvals and terminal. External MCP requires a real OAuth client and
  capability/permissions probe, not a mere `tools/list` response.

These are distinct gates. A skipped live test is **not** live acceptance,
and ordinary repository CI cannot claim remote pairing or paid model execution.
Record the exact T3 release, provider and Runner revision when performing
live acceptance. Set `T3CODE_VERSION` as a GitHub Actions repository variable
to pin the tested T3 release; an unset value follows the official installer
default and is not a reproducible release gate.

## Owner-only native pairing

When T3 is ready, the owner-private Environment inspection provides a
`services.t3.accessUrl` pointing at the Runner control plane. The Workbench
**Verify identity and connect T3** action opens this URL, **not** a pairing
credential. The browser follows Runner's existing GitHub OAuth authorization-code
flow with PKCE, a single-use state and an HttpOnly browser-binding cookie. The
GitHub numeric user identity is checked against the owning Environment before
a native T3 pairing credential is requested.

The authorized control plane sends a one-time pairing request over the exact
generation-bound runtime WebSocket. The runtime invokes `t3 auth pairing create`
on the host with `--ttl 5m --json` and its observed HTTPS tunnel origin, then
passes the pair URL back only through the still-open private request, not through
standard Task, MCP or Resource outputs or durable state. The browser is
redirected directly to T3's `/pair` page. The pairing token is in the URL
fragment and will never be included in the request URL sent to T3's HTTP server.
All T3 permissions remain native. Re-authenticate to mint a fresh pairing link;
a closed Environment cannot issue one.

## Headless MCP verification

The credential-free `T3 service smoke` workflow also exercises the official
MCP SDK with a five-minute, read-only native Bearer Session. It verifies real
`initialize`, `tools/list`, project read, denial of thread mutations and
revocation. T3 CLI `auth session issue` and `auth session revoke` are used on
the host, without exposing session bearer tokens in workflow logs. Native Bearer
tests are **not** a substitute for a separate external-client OAuth browser
consent and permission verification.

The optional `T3_LIVE_MODEL=1` test uses the official `thread start --wait --json`
command and checks the actual provider-completed reply, rather than creating an
empty thread or assuming a native Runner ACP Agent was involved.
